Product Review · 2026

一个内容很扎实的育儿小程序，
卡在了「入口」和「信任」上

12 个页面、6234 行数据与算法层、67 种食材、18 种疫苗、约 800 项测试断言 —— 这不是一个todo式的小项目。 但从产品视角看，它把最重的功能放在了最深的入口，把最重要的三个卖点里有两个交给了「用户自己配」。 这份报告拆开它的页面结构，找出真正的瓶颈。

12 个页面 4 个 tab（无图标） 0 个用户账号 0 处加载状态 6234 行 data + utils

一句话定位：这是一款「0–3 岁照护助手」，本质是内容库 + 规则引擎 + 本地记录本。 它的三条卖点是：① 按月龄给吃 / 动 / 学 / 睡建议；② 天气 → 穿衣层数 + 睡袋 TOG；③ 疫苗护理； 隐藏的第四条、也是做得最重的：辅食排敏 + 餐单生成。

业务与技术的真实构成

页面层（.js + .wxml）合计约 4000 行；而支撑层（data/ + utils/）有 6234 行， 其中 utils/food.js 1430 行、utils/store.js 964 行。 支撑层大于页面层，说明这个产品的价值主要沉淀在规则与内容里，而不是界面里 —— 这是好事，也解释了后面所有问题的由来。

04

投入 vs 触达：最重的页面，在最深的角落

横轴是预估使用频次（基于入口深度与场景推演，非埋点数据），纵轴是 JS 行数，气泡大小是 wxss 行数（即视觉投入量）。

两个气泡够说明问题： 「辅食」是全项目投入最重的页面（JS 473、wxss 1106），却落在左侧三级深链区； 「卡片」只承担一次分享，却拿到了唯一的骨架屏和一门 Canvas 绘制库。 资源分配不是按用户价值，而是按「哪个做起来更有意思」。
05

优缺点：好的是真资产，差的是系统性

每一条都回答「这在产品上意味着什么」，而不是罗列代码现象。

值得被保护的优势
01内容是结构化资产，不是占位文案
67 种食材带月龄门槛、过敏原标记、铁含量；18 种疫苗带反应清单与危险信号；9 档温度带的穿衣规则。这些内容有专业壁垒，是可迁移到任何平台的护城河。
02是「规则引擎」而不是「静态文章」
餐单生成有加权随机 + 固定种子（同一天打开结果稳定，换天会变），穿衣是温度 × 月龄双维查表，疫苗按接种后分期给护理。这意味着它能给出「你家宝宝此刻」的答案，而不是通用科普 —— 这是它区别于母婴公众号的唯一理由。
03数据层收口干净，可测试
11 个存储 key 全部走 utils/store.js 单一入口，utils/* 是纯函数。所以它才有能力跑出约 800 条断言 —— 这是一个能安全重构的代码库，也意味着后面的改造不会失控。
04天气三级降级 + 合规意识
云函数 → 直连 → 30 分钟本地缓存 → 离线兜底标注「离线缓存」；12 个页面统一挂医疗免责声明组件。说明作者对「不误导用户」是有敬畏的。
需要正视的问题
01定位撕裂：今日页在为三种产品同时妥协
内容产品要让人「逛」，工具要「3 秒出答案」，记录产品要「零摩擦记一笔」。今日页三件都做，结果三件都不极致。证据就在 tabBar 里：4 个 tab 全是「查」，但唯一有数据沉淀的模块全在二级以外 —— 团队内心当自己是内容产品，而留存只能来自记录。
02一级导航按开发模块切，不按用户任务切
今日 / 天气 / 疫苗 / 带娃人 = 1 个看板 + 2 个查询 + 1 个设置，缺「记录」和「我的宝宝」。这不是入口深浅的问题，是分类维度错了。用户想的是「我刚喂完，记一下」，导航想的是「这是辅食模块」。
03三个卖点里两个默认残缺，且残缺写在了脸上
首页写「需部署 weather 云函数」，设置页写「未配置模板 ID」，地点页写「未配置地图 Key」。对一个要发给别人用的小程序，这等于把「半成品」直接交付给用户。三条卖点里穿衣和推送两条默认不工作。
04交互诚信：假刷新、伪按钮、toast 万能
下拉刷新是固定 800ms 后强制停止；两处「可以自己加」点了没反应；约 54 处 toast 承担全部提示，0 处 loading。它训练出的是「这个产品的反馈不可信」—— 用户不会报 bug，只会停止点击。
05数据不可携带，且损失是沉默的
无登录、无账号、11 个 key 全在本机，换手机即全部归零。对记录型产品，这是最危险的一类问题：用户投入越多，损失越大，而他不会投诉，只会卸载并在群里说一句「别用了，会丢」。
06投入与触达倒挂
最重的辅食页在最深的入口，最轻的卡片页拿到最好的体验待遇。结果是：做得最用心的部分，最少人看见。

07

改造路线：按「不可逆损失」排序，不按工作量

排序原则只有一条：哪件事不做，用户会永久流失且不会告诉你。技术上容易改 ≠ 优先级高。

P0天气兜底：把「温度」的输入权还给用户
为什么是 P0
三块核心能力之一默认不工作。但真正的原因不是「没配环境 ID」，而是可用性被赌在一个部署动作上。天气页其实已经证明了解法：它的「室温 ± 手动覆盖 → 重算整张 TOG 表」就是同一个思路。
怎么做
在天气卡加「手输温度 / 选城市 / 选内置温度带」三选一，走通后再顺手删掉三处开发者文案：index.wxml:99、weather.wxml:28、place.wxml:56。先让能力可用，文案会自己消失。只删文案不改逻辑，等于把残废藏起来。
P0数据知情权 + 一键可带走
为什么是 P0
记录的不可逆损失是沉默的：用户不报 bug，只卸载 + 劝退。而且现在用户最少，恰是迁移成本最低的时点；等有量再补账号，历史数据已经回填不回来了。
怎么做
不做账号也能解决的版本：① 在宝宝档案页明确写「数据仅存本机」；② 提供导出 / 导入备份（把 store.js 的 11 个 KEYS 全量序列化成一段文本或二维码）。账号上云留到 P1，不要卡在这一步。
P0今日页首屏加「记一笔」
为什么是 P0
这是入口问题的正解，而且比加 tab 便宜得多。4 个 tab 里 3 个是「查」，唯一能产生留存的动作全靠深链。改首屏一行，收益大于重做导航。
怎么做
在 pages/index/index.wxml 宝宝卡下方加一组常驻快捷入口：记一餐 / 记辅食 / 记接种 / 记便便，直达 meal-log、food-edit。顺手把最近 3 条记录展示出来 —— 让用户看到「我记的东西在积累」。
P0交互诚信整改
为什么是 P0
假刷新 + 伪按钮 + 只有 toast 没有 loading，会训练出「这个产品的反馈不可信」。这是信任税，交久了就没人再点。
怎么做
① 假下拉改真刷新或直接去掉（index.js:32-34、weather.js:31-33）；② 伪按钮补 bindtap 或删除（food-edit.wxml:28、vaccine-edit.wxml:19）；③ 给 meal-log / food 这类重页面补骨架屏。
P1导航补「记录」与「辅食」，并给 tabBar 补图标
为什么放 P1 不放 P0
辅食有月龄窗口（约 6–24 个月），不是每个人都需要；而且再加第 5 个纯文字 tab 只会让现有的无图标导航更糊。所以这两件事必须一起做。
怎么做
先补 4 组 tab 图标（app.json:40-57 目前无 iconPath），再把「辅食」提上来；或更彻底一步：一级导航按任务重组为「今日 / 记录 / 查一下 / 我的」。
P1打通「推送给带娃人」，或诚实地降级
为什么重要
这是产品里唯一的增长机制：一个带娃人拉来另一个带娃人。现在它被一句「去公众平台申请模板」堵死（family.js:89-97、app.js:8）。
怎么做
短期：把它从「每日提醒」明确改成「生成卡片手动转发」，文案承诺和能力对齐。长期：这本来就是唯一可行的社交裂变点，值得单独设计。
P1重做「月龄建议」页
为什么重要
它同时是两个东西：内容的消费入口，和辅食的唯一大门。但正文全是「· 一句话」的圆点行，字级从 44rpx 直接跳到 20rpx。内容型页面不该长成待办清单。
怎么做
做「一条主建议 + 若干可展开细项」的层次；把辅食卡从「内嵌小卡」升级为页面级主入口；补齐分享（它是最想被转发给家人的一页）。
P2工程与打磨
内容
引入设计 token 收敛 206 个唯一色值（#B3A294 vs #B3A195 这类漂移）；随业务增长做分包，把 data/ 与 food 相关下沉；表单加范围校验（baby-edit.js:128-133 体重身高不校验）；长列表上拉分页；补无障碍。
判断依据
这些都影响「专业感」但不影响「能不能用」。在 P0 的信任问题解决之前，做这些属于优化一个用户还没决定要不要留下来的产品。
如果你只能做一件事：做 P0-1（天气兜底 + 删文案）。 因为它用最小的改动，同时解决「核心能力不可用」和「半成品观感」两个最伤信任的问题， 并且天气页已有的手动室温覆盖就是现成的实现范式，不需要新设计。
它已经是一个「有用的东西」，但还不是一个「别人愿意推荐的东西」。
差距不在功能，在第一步的可用性和第三步的可信度。

内容与规则是这三年攒下来的真资产，改造的核心不是重写，而是把这些资产挪到用户走得到的地方，并停止把配置责任转嫁给使用者。
