# 小芽日常 · 婴幼儿日常照护小程序

按月龄给出「吃 / 动 / 学 / 睡」建议，按**小区级位置**取天气算出今天该穿什么，再一键推给一起带娃的人。

---

## 一、功能

| 模块 | 说明 |
|---|---|
| 宝宝档案 | 小名、性别、出生日期、体重、身高、备注；支持多宝宝切换，全部存本机 |
| 月龄建议 | 0–36 月分 8 个档（0-1 / 2-3 / 4-5 / 6-8 / 9-11 / 12-17 / 18-23 / 24-36），每档含吃、动、学、睡四段 + 注意事项，可左右切换查看前后月龄 |
| 地点（北京市 → 区 → 小区） | 三级精确到小区；支持常用地点（家 / 奶奶家）一键切换；山区自动计入温差 |
| 天气穿衣 | 按地点坐标取 Open-Meteo（免密钥）：气温、体感、风力、湿度、紫外线、降水概率、最高最低温 → **温度 × 月龄双维**规则引擎，输出该月龄的具体款式（内层/外层/头部）+ 睡袋温度对照表 + 情境提醒 |
| 疫苗护理 | 记录疫苗类型、剂次、接种日期；按疫苗类型和「接种后经过多久」给出分阶段注意事项（留观 / 当天 / 1-3 天 / 3-14 天）+ 可能出现的反应 + 就医警示 + 下一针；接种记录只展示近 3 次、可展开全部；选未来日期则进「待安排疫苗」列表，到期自动转为接种记录；打了五联会自动覆盖百白破与脊灰，也可手动移除某一针；内置清单没有的自费疫苗可以自己加 |
| 辅食喂养 | 记账 + 计划两层。**排敏台账**：记录每次新食材尝试与反应（四档分级 + 严重反应当场就医提示），按「记录日 + 2 天」推进观察窗，同时加两种会警告分不清来源；67 种食材 / 47 个食谱 / 5 档月龄 + 12 个月龄节点，按宝宝实际月龄推荐下一个该试什么。**进食流水账**：一餐一条记吃了什么、多少、爱不爱吃，吃过但没记排敏的会反过来提醒补记。**接着三天**：今天起滚动的 3 天餐单，每天每餐给一句「为什么排它」，季节性食材只加权不硬筛，接种后 72 小时内自动收紧成「只吃吃过的」 |
| 推送给指定人 | 生成一张 1280px 宽的「今日卡片」（含地点），可转发微信好友/群、保存相册、复制文字版；家人名单支持勾选推送对象 |
| 每日提醒（可选） | 走微信订阅消息，需自行申请模板 ID |

## 二、地点精度：北京市 → 区 → 小区

### 数据模型

```js
place = {
  city: '北京市',
  district: '朝阳区',
  community: '望京西园',
  address: '北京市朝阳区望京街道望京西园四区',  // 地图返回的原始地址
  lat: 39.9963, lon: 116.4715,
  source: 'poi' | 'map' | 'district' | 'manual'
}
```

- `settings.place` 是当前生效地点，`settings.places` 是常用地点列表，`settings.activePlaceId` 指向当前那一项。
- 旧版本只存了 `city / lat / lon` 的，`getSettings()` 里会自动迁移成上面的结构（`utils/place.js` 的 `migrateLegacy`）。

### 小区是怎么拿到的（四条路，按可用性自动降级）

| 路径 | 依赖 | 拿到什么 | 何时用 |
|---|---|---|---|
| ① `place` 云函数搜 POI | 腾讯位置服务 WebService Key | 小区名 + 区 + 精确坐标 | 配了 key 时最顺，输入「望京西园」直接出候选 |
| ② `wx.choosePoi` | 微信「位置接口」权限 | 小区名 + 地址 + 坐标 | 没 key 时的首选，微信内置 POI 搜索器 |
| ③ `wx.chooseLocation` | 微信「位置接口」权限 | 坐标 + 附近地址 | ②不可用时的地图选点 |
| ④ 手填小区名 | 无 | 小区名 + **区中心坐标** | 永远可用，保证功能不阻塞 |

关键取舍：**区级一定可用**（内置北京 16 区中心坐标），小区级是「锦上添花」。没有地图 key、没有位置权限，用户依然能完成设置并拿到天气，不会卡在授权页。

### 配腾讯位置 Key（可选，但推荐）

1. 腾讯位置服务控制台 → 应用管理 → 创建 Key → 勾选「WebServiceAPI」
2. 云开发控制台 → 云函数 → `place` → 配置 → 环境变量：`TMAP_KEY = 你的key`
3. 重新部署 `place` 云函数

配好后额外解锁两件事：输入即搜的小区候选列表、以及「用当前位置」时自动反查区县和小区名（逆地理编码）。

### 山区修正

门头沟、房山、怀柔、平谷、密云、延庆六个区含较大海拔落差，`utils/place.js` 里标了 `mountain: true`。命中后：

- 温度先扣 2℃ 再匹配穿衣档（`clothing.recommend` 的 `mountain` / `mountainOffset` 参数）
- 依据行会写明「按体感 19℃，山区 -2℃，10 月龄 -2℃ 修正为 15℃」
- 注意事项里追加一条山区温差提示

> 注意：穿衣档宽约 3℃，所以 2℃ 的修正不保证一定跨档。文案写的是「已把这段温差算进去」而不是「已降一档」，避免说了没做到。

### 天气真的会不一样吗

Open-Meteo 的网格分辨率约 1–11 km，**同城区内不同小区差别很小**，小区级的主要价值是：① 山区/城郊交界处差异真实存在；② 卡片和推送里能明确写出「朝阳区·望京西园」，长辈一眼知道是给哪个孩子的。这点在 README 里说实话，比夸大精度更有用。

## 三、穿衣引擎：温度 × 月龄

穿衣不是按温度查一句「多穿点」，而是**两个维度交叉**：温度档（9 档）× 月龄阶段（5 段）。

### 为什么加月龄维度

只用温度，会给出「长袖薄棉连体衣 + 开衫」这种放之四海皆可、但不像婴儿装的答案。8 个月的宝宝在 22℃ 该穿**春秋连体衣**，16℃ 该穿**夹棉连体衣**——同一个温度下，2 个月和 30 个月的衣服根本不是一类东西：

| 修正后温度 | 2 月龄（新生儿） | 8 月龄（爬行期） | 30 月龄（幼儿期） |
|---|---|---|---|
| 18℃ | 夹棉和尚服 + 夹棉抱被 | 春秋连体衣（毛圈）+ 薄夹棉马甲 | 长袖 T 恤 + 卫衣 + 长裤 |
| 12℃ | 薄棉内衣 + 夹棉和尚服 | 夹棉连体衣 + 夹棉外出服 | 加绒卫衣 + 加绒长裤 + 夹棉外套 |

### 匹配流程

1. 取**体感温度**（不是气温）
2. 月龄温度修正：<3 月 −3℃、3–12 月 −2℃、12–24 月 0、≥24 月 +1℃
3. 山区再 −2℃（门头沟 / 房山 / 怀柔 / 平谷 / 密云 / 延庆）
4. 落入 9 个温度档之一（极冷 / 严寒 / 较冷 / 冷 / 凉 / 微凉 / 舒适 / 偏热 / 炎热）
5. 用「温度档 × 月龄阶段」查出**该月龄的具体款式**，输出内层 / 外层 / 头部三层
6. 叠加情境提醒：温差 ≥8℃、风力 ≥6 级、雨雪、紫外线 ≥6、闷热高湿、极寒、≥32℃、6 月龄内捂热风险

月龄阶段与款式取向：

| 阶段 | 月龄 | 主打款式 | 注意 |
|---|---|---|---|
| 新生儿 | 0-2 | 和尚服、包屁衣、抱被 | 前开襟，换尿布不折腾脖子 |
| 小婴儿 | 3-5 | 一体式连体衣 | 还不会独坐，护住肚子 |
| 爬行期 | 6-11 | 春秋连体衣、夹棉连体衣、分腿款 | 爬得多易出汗，别穿长袍 |
| 学步期 | 12-23 | 分体：卫衣 + 长裤 | 裤腰别太紧，留纸尿裤空间 |
| 幼儿期 | 24-36 | 好穿脱的分体 | 活动量大，宁可少一件 |

### 睡袋：给一整张区间表，而不是一个数

只给一个 TOG，家长遇到「明晚降温 5 度」还得再问一次。所以睡袋改成**表格 + 当前档高亮**，7 个室温区间全部列出：

| 室温 | 睡袋 | 穿盖 |
|---|---|---|
| ≥28℃ | 0.2-0.5 TOG | 无袖睡袋，或只穿短袖包屁衣 |
| 26-27℃ | 0.5 TOG | 短袖包屁衣 + 0.5 TOG 睡袋 |
| 24-25℃ | 1.0 TOG | 短袖 / 薄长袖连体衣 + 1.0 TOG 睡袋 |
| 21-23℃ | 1.5 TOG | 长袖连体衣 + 1.5 TOG 睡袋 |
| 18-20℃ | 2.5 TOG | 长袖连体衣 + 2.5 TOG 睡袋 |
| 15-17℃ | 3.0 TOG | 加厚长袖连体衣 + 3.0 TOG 睡袋 |
| ＜15℃ | 3.5 TOG | 3.5 TOG 睡袋 + 长袖保暖内衣 |

- 当前室温那一行会高亮并标「当前」，其余行当参考表用。
- 睡袋**款式也按月龄给**：0-5 月一体式 / 襁褓（会翻身即停用襁褓），6 月龄以上分腿睡袋。
- 室温由室外体感**分段估算**：≤8℃ → 21℃（供暖季，室温被暖气锚住）、8–23℃ → 线性过渡到 23℃（停暖 / 开窗）、>23℃ → 继续上浮；结果夹在 10–33℃。
- 卡片上有 **室温 −/＋ 步进器**：家里有温度计就按实测改，整张表会重算并重新高亮，改动后标「手动」，可一键「恢复估算」。

> **两个坑都是写测试时才发现的。**
> 一是室内温度**不参与月龄修正**——房间冷不冷跟宝宝几个月大没关系，否则同一天气下两个孩子的室温会算得不一样。
> 二是最早的估算是「室外 + 4℃」，室外 −5℃ 会算出室内 −1℃，于是推荐 3.5 TOG。暖气房里捂到 3.5 TOG 是实打实的捂热风险（婴儿过热与 SIDS 相关），所以改成供暖锚定：室外 −5℃ 稳定落在 21℃ → 1.5 TOG。

## 四、疫苗护理：记录一针，给一段时间的注意事项

打针本身只要几分钟，麻烦的是之后三天：该不该测体温、针眼化脓了要不要挤、什么时候出现反应算正常。所以这一块不是「疫苗清单」，而是**按接种后的时间推进的护理脚本**。

### 记一条要填什么

疫苗（18 种：10 种一类免费 + 8 种二类自费）、第几剂、**接种日期**、门诊、备注。

页面上没有「具体时间」这个输入框——家长手里只有接种证上那个日期，追问几点几分只是给自己添麻烦。引擎内部统一按当天 09:00 计（门诊基本上午开诊），「留观 30 分钟」「接种后 24 小时」这些节点仍然成立。

### 记录两种命运：已发生的进记录，未来的进「待安排」

保存时如果日期**晚于今天**，这条记录不会混进接种记录里，而是进「待安排疫苗」列表——因为它还没发生：

| | 接种记录 | 待安排疫苗 |
|---|---|---|
| 触发条件 | 日期 ≤ 今天 | 日期 > 今天 |
| 参与护理提醒 | 是 | 否（没打就没有反应可护理） |
| 计入「已接种 N 针」统计 | 是 | 否 |
| 把免疫规划表对应行标成已接种 | 是 | 否（那行仍然是「快到了」或「该打了」） |
| 排序 | 由近到远（最近的在最上面） | 由近到远（最近要打的在最上面） |

「待安排」每行显示「日期 / 疫苗名 · 第 N 剂 / 还有几天 + 门诊」，点进去可以改日期或删掉。等日期过去了，这条记录自动出现在接种记录里，并开始按阶段推送护理事项——不需要手动搬。

这样做的理由很实在：把「约好下周三去打」和「上周三已经打完」混在一张列表里，会让护理引擎对着一针还没打的疫苗喊「今天可能低热」。

### 接种记录只展示近 3 次

记录攒起来以后一屏铺不完，所以默认只留最近 3 次，标题栏右侧显示「展示全部 N 次」，点开展开全量、再点收起。卡片底部同时给一句「共 N 次 · 免费 X · 自费 Y」，不用展开也知道总共打了多少。

### 护理分成 5 个阶段

| 阶段 | 时间窗 | 核心任务 |
|---|---|---|
| 留观中 | 0–30 分钟 | 不许提前走；看脸色、呼吸、有没有出冷汗 |
| 接种当天 | 0.5–24 小时 | 每 4 小时测体温；针眼不揉、不泡澡；多喂一次奶 |
| 1–3 天 | 24–72 小时 | 早晚各测一次体温；红肿硬结别热敷；辅食清淡 |
| 3–14 天 | 72–336 小时 | 盯减毒活疫苗的**迟发**反应；卡介苗的卡疤进程 |
| 观察期已过 | >14 天 | 正常照护，去看下一针什么时候 |

### 同一阶段，不同疫苗给的话不一样

这是这个模块最关键的部分——通用护理模板是不够用的：

| 疫苗 | 特异性提示（覆盖通用模板之上） |
|---|---|
| 卡介苗 | 2–3 周局部红肿→化脓→结痂是**正常过程**，别挤别涂药别包扎；3 个月没卡疤要复查 |
| 麻腮风 / 乙脑 / 水痘 | 反应常在第 5–12 天（水痘 2–3 周）才出现，那时打针已经过去很久，家长容易想不到 |
| 脊灰（口服） | 服苗前后 30 分钟不吃热食、不喝热水；免疫缺陷改用 IPV |
| 轮状（口服） | 疫苗病毒随大便排出，换尿布后洗手；阵发性哭闹 + 呕吐 + 果酱样便要急诊（肠套叠） |
| 百白破 / 五联 / 13 价肺炎 | 反应比别的针明显，4–6 小时后开始低热，48 小时内多能退 |
| 乙肝 | 第 1 剂必须在出生 24 小时内；母亲 HBsAg 阳性要同时打免疫球蛋白 |
| 流感 | 6 月龄以下不能打，靠家里人接种形成保护圈 |

反应还按时间窗分成两类展示：
- **此时可能出现**（当前已进入该反应的时间窗）
- **接下来可能出现**（带「5 天后」这种倒计时）——麻腮风打完第 2 天，页面就会预告「5 天后可能低热、出疹」，免得家长以为是别的原因。

### 记录之外：对照免疫规划表

`data/vaccines.js` 里的 `PLAN` 是 22 行的一类疫苗接种程序（出生 → 6 岁）。拿宝宝月龄和已记录剂次一比，得出四种状态：

`已接种` / `该打了` / `已过建议月龄`（超过 2 个月没记录）/ `快到了`（1 个月内）

这张表收在页面底部的折叠区里，不占首页版面——它是一张「查阅型」的表，家长想核对时才展开，而不是每天弹一个卡片催打针。早先版本在顶部放过一张「按免疫规划表，这些该安排了」的摘要卡，和上面「待安排疫苗」的语义打架（一个是你自己约好的，一个是程序表推算的），所以删掉了，只保留这一处可折叠的全表。

- 一针都没记过时，表标题不会写「该打乙肝了」（对一个 8 月龄宝宝没意义），而是「还有 13 针没记录」，并把**当前月龄刚到期**的那几针排在前面。
- 二类疫苗不进这张表——自费疫苗按家庭和门诊建议自行选择，不替家长做决定。

### 打联合疫苗后，被覆盖的单苗自动让位

五联打完，规划表里的百白破和脊灰就不该再催——所以引擎里有一张替代关系表（`COVER_RULES`）：

| 打了 | 覆盖规划表里的 |
|---|---|
| 五联疫苗 | 百白破 1–4 剂、脊灰 1–3 剂（**脊灰第 4 剂在 4 岁，五联不含，仍单独提醒**） |
| 甲肝灭活 | 甲肝减毒活（二者二选一） |

覆盖是**按剂次逐条推导**的：只打了 1 剂五联，就只覆盖百白破第 1 剂和脊灰第 1 剂，不会一口气把 4 针都划掉。被覆盖的行显示成「已覆盖」，点一下会说明是哪一针覆盖的、想取消就删那条记录。

### 也能手动移除某一针

不是所有情况都能靠规则推导：外地打过了没带回来、医生建议暂缓、孩子有禁忌症……所以每一行都可以点开选择：

- **标记为已接种** → 跳到记录页并预选好疫苗和剂次
- **不再提醒这一针** → 从表里移走，收进底部「已移除 N 项」，随时可以恢复

状态优先级：`已接种` > `已覆盖` > `已移除` > 按时间推导的四种。移走的东西不会真的消失，避免「点错了找不回来」。

### 内置清单没有的疫苗，自己加

二类疫苗的厂家和品种太杂（各地门诊供应的手足口、轮状、13 价程序都不一样），硬编码清单一定会漏。所以记录页的二类分类末尾有个「＋ 自定义」：

- 填名称、剂次数（1–6）、备注，保存后立刻可以记录接种
- 自定义疫苗**没有专属护理知识库**，护理页只给通用事项，并明确写一句「这是你自己添加的疫苗，按通用事项护理，具体看说明书」——不假装懂
- 它不进免疫规划表（自费苗不替你安排时间），删除时会提示会连带清掉多少条记录

## 五、辅食喂养：排敏台账 + 今天吃什么

辅食类小程序已经很多，纯菜谱没有差异化。家长真正会卡住的地方是三件事：该加什么、加了之后有没有过敏、今天到底做什么。所以这一块的重心是**排敏**，菜谱只是配套。

### 记一条要填什么

食材、尝试日期、反应（四档）、备注。**只记「第一次吃某种新食材」**，不是每日喂养流水账——流水账没人能坚持记。

食材从内置的 67 种里选（按谷薯/蔬菜/水果/肉/肝/鱼虾/蛋/奶/豆/坚果/油分 11 组），找不到的可以自己加，自定义食材会明确标注「App 没有它的专属资料」。

### 观察窗：3 个日历日

记下的那天算第 1 天，之后两天还在窗内。这段时间主页会一直显示「正在排敏：南瓜 · 第 2 天，还要看 1 天」，并提示先别加新的。第 4 天才算通过。

这个窗口不是拍脑袋定的——「一次只加一种、观察 2-3 天」是儿科喂养指导里最基础的一条，但落到生活里很容易忘，所以做成了会自己推进的状态。

### 冲突检测：一次只加一种

如果观察窗内又记了另一种新食材，主页会黄条提示「同时有两种新食材在观察，万一有反应会分不清是哪个」。**这是纯菜谱类产品给不出的东西**——它需要知道「你上次什么时候加的什么」。

### 反应分四档，处置不同

| 记录 | 页面文案 | 后续 |
|---|---|---|
| 没问题 | 吃完 3 天内没有异常 | 留下，可与其他已通过食材搭配 |
| 轻微反应 | 口周红、少量湿疹、放屁多、便便变稀 | 停 1-2 周，再用更少的量试一次 |
| 明确过敏 | 皮疹扩散、呕吐、腹泻、明显哭闹 | 停 3-6 个月，就诊时告知具体食材 |
| 严重反应 | 呼吸急促、嘴唇/眼睑肿、声音嘶哑、精神差、血便 | **立即就医或拨 120**，这类食材以后一律不再试 |

选了「严重反应」时，编辑页会**当场**弹红底提示条（不是保存后才提示），文案是「别在这里记录了，先就医或拨 120」。

### 待尝试：按实际月龄，而不是按粗档推荐

5 个阶段档（6-8 / 9-11 / 12-17 / 18-23 / 24-36）对「记录该记什么」够用，对「现在该加什么」太粗：6、7、8 三个月家长要做的事完全不同。所以又加了一层**逐月刻度** `MONTH_FOCUS`，12 个节点（6/7/8/9/10/11/12/15/18/24/30/36），每个节点给四样东西：

| 字段 | 例子（第 7 个月） |
| --- | --- |
| `title` | 第 7 个月 · 该加肉泥了 |
| `focus` | 红肉泥要进来了——6 月龄后从母体获得的铁基本用完，只靠米粉不够 |
| `texture` / `meals` | 稠糊 / 1-2 餐/天（覆盖阶段档的值） |
| `next` | 猪肉、牛肉、鸡肉、蛋黄、西兰花、菠菜、小米、梨、牛油果 |

`next` 直接决定「待尝试」列表的头部。排序分四层：

1. **还没吃过强化铁米粉（≤12 月龄）**：排在所有东西前面。「第一口是米粉」这条不因为月龄往后走就失效
2. **本月重点**（`MONTH_FOCUS[at].next`）：严格按数据里的顺序
3. **刚到月龄**（`fromMonth === 本月`）：同月的新食材兜底，铁优先
4. **补课**（`fromMonth < 本月`）：之前漏掉的，离现在近的先补；再往后才是阶段顺序

效果（什么都没记录时）：

```
6 月龄  强化铁米粉 → 南瓜 → 胡萝卜 → 苹果 → 香蕉 → 土豆
7 月龄  强化铁米粉 → 猪肉 → 牛肉 → 鸡肉 → 蛋黄 → 西兰花
8 月龄  强化铁米粉 → 猪肝 → 鳕鱼 → 三文鱼 → 鲈鱼 → 豆腐
```

跟上进度之后（米粉那批吃过了）：

```
7 月龄  猪肉 → 牛肉 → 鸡肉 → 蛋黄 → 西兰花 → 菠菜
8 月龄  猪肝 → 鳕鱼 → 三文鱼 → 鲈鱼 → 豆腐 → 燕麦
9 月龄  宝宝面条 → 番茄 → 白菜 → 大米软饭 → 奶酪 → 桃
```

已经试过的、正在观察的、出过过敏的、还没到月龄的、以及家长点了「先不试」的，都不会出现在这个列表里。跳过的收在「已跳过 N 种 · 恢复」里，随时能找回来。

节点之外的月龄取**最近的上一档**（13、14 月龄都按第 12 个月给），页面上会说明「当前月龄没有单独一档，按第 12 个月的进度给」，不装作是精确值。

**「不想试」是按宝宝隔离的**（存 `babyId#foodId`）。疫苗模块的 `planHidden` 是全局的，多宝宝会互相污染，这里没有重复那个坑。

### 今天吃什么 / 一周餐单

两个都是**现算不存库**的：用 `babyId + 周一日期 + 月龄` 做伪随机种子生成。

- 同一周任何时候打开，菜单完全一致（不会「昨天看的不一样」）
- 跨周自动换新，家长零维护，也不存在「计划过期」这种状态
- 9 月龄和 10 月龄不是同一份——月龄进了种子，长大一岁菜单跟着换
- 只把**手动换掉的那一格**存下来（`menuSwap`，按 `日期#餐次` 记），读时优先用替换值

每餐的候选按食谱的 `meal`（早餐/午餐/晚餐/加餐/任意）和月龄区间过滤，同一天内不重复，同一周内尽量不重复。

**只有一种情况会让同一个日期换菜：接种后 72 小时内的收紧**。那三天里候选会先收窄到「不含没试过的过敏原」，再收窄到「食材全吃过」，收窄后候选空出来时才放宽（见下面「季节与接种期」）。

#### 质地递进：别在 9 月龄还推 6 月龄的纯泥

光按 `fromMonth..toMonth` 过滤不够——「红薯泥」写的是 6-11 月龄，结果 10 月龄还在排它。所以加了两道约束：

- **优先「本月或上个月才解锁」的食谱**（`r.fromMonth >= 月龄 - 1`）。候选少于 2 道时不筛——宁可重复，也不能只剩一道菜天天见
- 6 月龄那批纯泥的 `toMonth` 收到 8-9 月龄，加餐不再退回到纯泥（9-11 月龄的下午茶排的是蒸南瓜条 / 蒸苹果片 / 酸奶香蕉糊）
- 补了 9-11 月龄缺的加餐与 10 月龄以后的早餐，否则一筛就只剩一道菜

### 排敏优先：18 月龄以内不排含未试过敏原的菜

菜单生成时先看宝宝试过哪些过敏原组，**先只从「不含未试过敏原」的食谱里挑**，挑不出来才放宽，并在那一餐标「含还没试过的过敏原：鱼类」。

举个真实的例子：8 月龄的宝宝只试过米粉和南瓜，如果不管这个，餐单会随机排出「鳕鱼泥」——家长照着做了就是一次没有记录的排敏。所以第一次打开时，餐单基本只会出现米粉、南瓜泥、苹果泥这类零过敏原的菜；等蛋黄记过了，蛋黄米糊才会进早餐。

18 月龄以上不再做这个过滤——那时候食材基本都接触过，过滤只会把早餐压成一道菜反复出现。

**已经出过过敏（`allergy` / `severe`）的食材是硬排除**，不参与「放宽」这一步，任何月龄都不会排进餐单。顺带修了一个连带问题：`triedAllergenKeys` 原来把「过敏」也当成「已通过」，导致蛋黄过敏的宝宝餐单里照样排蛋黄米糊——现在明确过敏的那一组不算通过。

### 进食流水账：一餐一条，但绝不反哺排敏

排敏台账记的是「某种食材第一次吃 + 有没有反应」，一个食材一条；流水账记的是「这一餐吃了什么、吃了多少」，一餐一条。两张表分开存（`xyd_food_records` / `xyd_meal_logs`），因为语义不同：

```js
// 一餐一条，吃的是计划外的也可以记
{
  id, babyId, date, slot,            // slot: am|noon|pm|eve|other
  recipeId, recipeName,              // 菜名存快照，食谱改名不影响历史
  foods: ['pumpkin'],                // 从食谱带出来，可增减、可手选
  amount, amountText,                // 四档分量 + 选填「小半碗」这种自由文本
  accept, poop, note                 // 很爱吃/还行/不肯吃；便便四档选填
}
```

记一餐的入口有两处：辅食页底部「记一餐」，以及今天/明天/后天每道菜右边的「吃了」——后者会把日期、餐次、食谱一起带进表单，食材已经勾好，只剩「吃了多少、爱不爱吃」两个点选。

**关键取舍：流水账不改变排敏状态。**

如果让流水账里出现过的食材直接算「已尝试」，那么一个家长随手记的一餐，就会把这个食材从「待尝试」里静默挪走，他可能永远不会按「一次一种、观察 2 天」正式做一次排敏。这个模块唯一的差异化价值就是排敏，所以方向只能反过来：**用流水账发现台账的漏网**。

`untrackedFoods()` 会找出近 7 天吃过、但台账里没有的食材，在页面上给一条黄条，每项点一下就能跳去补记。过敏原排在最前面，因为那几类最值得补一条正式记录。已经被家长「先不试」的、以及已经被删掉的自定义食材，都不提醒。

流水账同样**不会自动生成排敏记录**——那等于凭空造一条「某天观察过、无反应」的假数据。只会提醒，不会代填。

数量上做了个安全阀：单宝宝超过 2000 条时按日期留最近的，正常用到 3 年也触发不了，留着是防单个 Storage key 的 1MB 上限。删宝宝时级联清空；删自定义食材时只把那个 id 从各餐的 `foods` 里摘掉，不删整条记录。

### 接着三天：按周切片，不掷新骰子

「今天起 3 天」听着像要为新窗口重新生成，其实不用。一个日期只属于一个 ISO 周，所以只要**按各自所在周调一次周餐单，再切片**就行：

```js
planFor(月龄, babyId, 起始日, 天数, swaps, today, records, opts)
  → 对窗口里出现的每个周一日期各调一次 menuFor，再按日期切出 N 天
```

由此得到的性质正是想要的：

- 今天看到的「明天」和明天打开看到的「今天」是同一道菜（跨天滚动不跳变）
- 3 天窗口里如果含周一，会跨两个周餐单，但**种子一个字没改**，周内去重照样成立
- 页面只调 1 次 `menuFor`（窗口不跨周时），一周餐单和 3 天计划共用同一份结果——首屏反而比原来「今天吃什么 + 一周餐单各算一遍」更快

每餐带一句 `reasons`（最多 3 条，按 `接种期` → `当季` → `本月重点` → `补铁` 排），也就是页面上那句「为什么排它」。这是纯派生字段，不消耗随机数，所以不影响餐单的确定性。

### 季节与接种期：一个只加权，一个硬收紧

两者的介入方式刻意不同。

**季节只做正向加权，绝不硬过滤。** 当季表（`SEASON_MONTHS`）是独立常量，35 种食材有明确月份，表里没有的算全年——肉、肝、蛋、奶、鱼虾、米粉、油都在这一类，没有「反季肉」这回事。加权规则：基础 10 分，含当季食材 +6，含本月重点食材 +4。

不做反季惩罚的理由有两条：11 月的暖棚番茄仍然是番茄，家长买得到就该能排；更实际的是负权重会压窄候选池，把本来就不多的食谱筛成两三道天天见。

「当季」在页面上的措辞固定是「11 月当季（秋）：南瓜、白菜、橙子 · 北方露地参考」，不写「只能吃这些」。它也不进 `dueFoods` 的排序——该加什么由月龄和铁决定，不该被时令左右。

**接种期是硬约束。** `dietFlagFor()` 取最近一条真实接种记录（未来日期的「待安排」必须先剔掉，否则小时数会被夹成 0 造出假的「刚打完」）：

| 接种后经过 | 级别 | 餐单怎么办 |
|---|---|---|
| < 24 小时 | `strict` | 只排「食材全都吃过」的食谱 |
| 24–72 小时 | `light` | 先剔掉「含没试过的过敏原」的食谱 |
| ≥ 72 小时 | `none` | 不干预 |

收窄一律是「**有才收窄**」：筛完如果候选空了，就退回上一步，绝不把餐位清空——宁可排一道略带新食材的菜，也不能出现「今天没得吃」。同理，`altRecipe`（换一道）也必须走同一套约束，否则「换一道」就成了绕过通道。

依赖方向是单向的：`utils/food.js` **不 require `vaccine.js`**。疫苗 flag 由页面算好，通过 `opts.diet` 注入引擎。这样辅食引擎的每个测试用例都不隐式依赖疫苗知识库，改疫苗文案也不会动到餐单断言。

### 明确不做的

- **不做克数 / 毫升 / 热量 / 营养配比**：分量只有四档 + 一句自由文本，任何「g」「ml」输入框都不给。做成必填字段只会让人放弃记
- **不让流水账反哺排敏状态**：会静默沉掉没做排敏的食材，与模块唯一价值冲突（只做反向提醒）
- **不做手动排整周餐单**：只做「自动生成 + 单格换一道 + 记一餐打卡」
- **不做过敏原「检测 / 判断」**：只记录与分级提示，页面统一口径「是否过敏由医生判断」
- **不做流水账的图表 / 导出 / 云同步**：只做「近 3 条 + 共 N 餐」的回顾，统计图会把人引向「营养分析」，那是这个模块明确不碰的方向

## 八、推送怎么做

## 十一、合规提示

- 每个页面底部都有免责声明：「内容为通用育儿照护参考，不构成医疗建议」。
- 服务类目建议选「工具」类（如 工具 > 信息查询）；**不要**选医疗健康类，本产品不做诊断、不提供用药建议。
- 用了 `requiredPrivateInfos` 的位置接口，提审时会被要求说明用途，按 `permission.scope.userLocation.desc` 那句话提交即可。

## 十二、已知限制

- 建议是年龄段通用参考，不针对早产、过敏、疾病等情况做个体化调整。
- 内置行政区划只有北京市 16 区。要扩到其他城市，在 `data/districts.js` 里加区县数组即可，其余逻辑不用动。
- 小区 POI 检索依赖腾讯位置服务 Key；没有 key 时只能用微信地图选点或手填。
- Open-Meteo 为境外服务，国内访问偶有波动；正式上线建议换和风/高德，只需改 `cloudfunctions/weather/index.js` 一个文件。
- 订阅消息一次授权一条，做不到「一次授权、长期自动推送」。
- 疫苗护理的文案是通用科普（依据国家免疫规划程序和疫苗说明书常见反应描述），**不能替代接种门诊的个体化告知**；早产、免疫缺陷、过敏体质、正在用激素或免疫球蛋白的宝宝，接种与护理一律听医生。
- 疫苗库覆盖 18 种常见疫苗，程序表只排一类疫苗；各地二类疫苗的厂家程序（如 13 价肺炎 2/4/6/12 或 3/4/5/12）有差异，以门诊方案为准。
- 自定义疫苗只是「记一笔」，没有专属护理知识，也不会进免疫规划表；替代关系表只写了五联→百白破/脊灰、甲肝灭活→甲肝减毒活这两组明确可替代的，其余联合疫苗（如四联、AC-Hib）需要自己在规划表里点「不再提醒」。
- 接种记录只存本机，没有云端同步；换手机或清缓存会丢，重要记录建议同时留在预防接种证上。
- 「待安排 → 接种记录」的搬家是在**打开页面时按当天日期现算**的，没有后台定时任务：约好的那天如果没打开小程序，护理提醒不会自己开始推送，第二天打开才会看到。
- 辅食的文案同样是通用科普（依据中国居民膳食指南与儿科喂养指导），**不能替代儿保门诊的个体化建议**；早产、低体重、有湿疹或过敏家族史的宝宝，辅食的起始时间与食材顺序一律听医生。
- 内置食材 67 种、食谱 47 个，覆盖的是常见家庭食材；各地时令菜、地方特色食材要靠「自定义」补，自定义食材没有专属资料，只给通用原则。
- 辅食的排敏观察窗按 **3 个日历日**统一处理，没有区分「低敏食材 2 天、高敏食材 3 天」这种更细的差异——真实的门诊指导本身也不统一。
- 一周餐单是**按种子确定性生成**的，不是营养师排的：它保证多样性、避开了未试过敏原，但不管营养配比是否最优化。
- 逐月刻度只有 12 个节点，13、14、16、17 这类月龄取的是「最近的上一档」，页面会写明是参照第几个月给的，不会假装精确。
- 食谱的质地递进靠「优先最近两个月解锁的菜」实现，不是按食材克数/颗粒直径的严格分级；某一餐候选少于 2 道时会退回全量候选，这时可能出现质地偏细的菜。
- 食谱没有做「几个人份」「按克数」的量化，只有步骤和性状——给 6 月龄宝宝称克数没意义，反而增加负担。
- 当季月份表是**北方露地**的粗略参考（35 种食材），同一食材在华南、西南的上市期会差一两个月；它只影响餐单里谁更容易被排到，不构成「这个月不该吃这个」的结论。
- 接种后的餐单收紧只按「最后一针的时间」算 72 小时，没有区分减毒活疫苗与灭活疫苗的差异；如门诊有特别交代（比如某种疫苗后要忌口更久），以门诊说法为准。
- 进食流水账是**一餐一条的回顾数据**，不参与任何营养计算，也不会自动生成排敏记录；想吃出「营养是否均衡」的结论，这个模块给不了。
